# 01. 시스템 개요 및 아키텍처

## 1. 프로젝트 개요

**Mini** (구 Phase 11)는 직장인의 반복적인 점심 의사결정 피로를 데이터 기반으로 해결하는 **end-to-end 점심 최적화 파이프라인**입니다. 카카오맵·기상청·식약처·에어코리아 4개 공공 API와 내부 사용자 데이터를 통합 수집·정제·분석하여, 거리·날씨·영양·팀 선호 4축의 가중 스코어링으로 최적의 점심 메뉴를 추천합니다.

### 1.1 목표 사용자 시나리오
- 매일 12시 직전, 팀원들이 "오늘 뭐 먹지?"를 1분 안에 합의
- 비 오는 날 → 가까운 국물 요리, 더운 날 → 시원한 면류 자동 우선순위
- 주간 영양 균형이 깨지면 → 단백질 위주 메뉴 제안
- 팀 투표 결과를 Slack으로 즉시 공유

### 1.2 핵심 가치 제안
| 항목 | 기존 방식 | Mini |
|---|---|---|
| 결정 시간 | 10–15분 | 1–2분 |
| 추천 근거 | 즉흥적 | 4축 정량 점수 |
| 영양 추적 | 없음 | 주간 자동 집계 |
| 팀 협업 | 메신저 분산 | Slack 통합 / 실시간 투표 |
| 자연어 상호작용 | 없음 | RAG 챗봇 + Tool Calling |

### 2.2 데이터 흐름 (Data Flow)

```
[외부 공공 API]
  ├─ 카카오맵 ──┐
  ├─ 기상청 ────┤
  ├─ 식약처 ────┼──> [4개 Collector] ──> [Transformer] ──> [SQLite]
  └─ 에어코리아─┘   (APScheduler 스케줄)    (스코어링)        ↓
                                                            ↓
[lunch-api 45 endpoints] ←── [4축 추천 엔진] ←──────────────┘
        ↓                          ↑
[dashboard-web 7 pages]            │
        ↓                          │
[nlp-api 18 endpoints] ←── 감성 ──┤
        ↓                  메뉴   │
[Ollama LLM (qwen2.5:7b)]  RAG ───┘
        ↓                  NLG
[ChromaDB 벡터스토어]
```

### 2.3 레이어 분리 원칙

| 레이어 | 디렉터리 | 책임 |
|---|---|---|
| **Presentation** | `dashboard-web/` | UI 렌더링, 사용자 인터랙션, 클라이언트 스코어링 |
| **API Gateway** | `lunch-optimizer/api/` | RESTful + WebSocket, 인증, CORS |
| **Domain Logic** | `lunch-optimizer/engine/`, `pipeline/` | 추천 알고리즘, 스코어링, 데이터 정제 |
| **Data Access** | `lunch-optimizer/database/` | SQLAlchemy ORM, 11개 테이블 |
| **NLP Service** | `NLP/nlp_mvp/`, `nlp_research/` | 감성/정규화/RAG/NLG/Tool Calling |
| **Infrastructure** | `docker/`, `.github/workflows/` | 컨테이너화, CI/CD, 배포 |

| B2 | Food NER | KoELECTRA + CRF (FOOD/INGREDIENT/ALLERGEN) |
| E1 | Embedding CF | Sentence-BERT + FAISS |

### 3.5 Phase 7 — Tool Calling

LLM이 lunch-optimizer 엔드포인트를 함수처럼 호출하는 8개 도구:
1. `get_lunch_recommendations` — 4축 종합 추천
2. `get_current_weather` — 현재 날씨
3. `get_nutrition_diagnosis` — 주간 영양 진단
4. `get_restaurant_info` — 음식점 상세
5. `cast_vote` — 투표 (쓰기)
6. `get_vote_status` — 투표 현황
7. `record_meal` — 식사 기록 (쓰기)
8. `get_visit_history` — 방문이력

## 7. 보안 / 권한 모델

- **인증**: 현재 미구현 (내부 트러스트 환경 가정), localStorage 기반 사용자 식별
- **CORS**: `localhost:3000`, `localhost:5173` 화이트리스트
- **Security Headers**: X-Content-Type-Options, X-Frame-Options, Referrer-Policy, X-XSS-Protection (FastAPI 미들웨어)
- **Rate Limit**: NLP의 비용이 큰 엔드포인트(챗봇)에 slowapi `@rate_limit("10/minute")` 적용
- **Secrets**: 모든 API 키는 `.env`에 보관, `.pre-commit-config.yaml`의 `detect-secrets`로 git 커밋 차단

## 8. 향후 확장 포인트

1. **모바일 앱** — React Native/Flutter로 dashboard-web 컴포넌트 재사용
2. **인증 강화** — JWT + OAuth 2.0 (Slack/Google), 관리자 권한 분리
3. **실시간성** — Vote/Chat을 WebSocket → WebRTC Datachannel 또는 Yjs로
4. **데이터 마트** — SQLite → PostgreSQL/TimescaleDB 마이그레이션 (시계열 분석 강화)
5. **모델 고도화** — Phase 6 ABSA/NER/CF 1,000+ 라벨링 후 학습 → 실서비스 투입
6. **분석 대시보드** — 팀 단위 트렌드 / 실패 결정 패턴 / 만족도 변화
